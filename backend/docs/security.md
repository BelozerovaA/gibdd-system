# Безопасность и известные ограничения

Проект учебный. Здесь честно описано, что сделано для безопасности, а что нужно доработать перед боевым использованием.

## Что реализовано

- **Вход по логину и паролю**, в ответ выдаётся JWT-токен с ограниченным сроком (по умолчанию 30 минут). Все маршруты, кроме входа, справочников и скачивания отчёта, требуют токен.
- **Данные только своего владельца.** История и оповещения фильтруются по текущему сотруднику, менять чужое оповещение нельзя (`404`). Удалить можно только свою запись розыска.
- **Отдельный токен для скачивания отчёта** (`scope = export`, 2 минуты). Ссылка на скачивание открывается в браузере, где нет заголовка `Authorization`, поэтому основной токен в адрес не кладётся. Токен с таким назначением не принимается ни остальными маршрутами, ни WebSocket.
- **Сервисы подтверждают друг друга общим секретом.** Сервис камер подписывает события заголовком `X-Service-Token`, сервис ГИБДД подписывает им список розыска. Токен сравнивается безопасным способом (`hmac.compare_digest`), а если он не задан на стороне получателя, приём закрыт целиком (`503`): лучше отказать, чем принимать запросы от кого угодно.
- **WebSocket проверяет токен** и то, что он принадлежит сотруднику из адреса; иначе соединение закрывается с кодом `4401`.
- **Секреты не хранятся в репозитории:** `.env` и `seed_users.json` исключены через `.gitignore`, в git лежат только шаблоны `.env.example` и `seed_users.example.json`. Пароли не печатаются в консоль при входе и при заполнении БД.

## Ограничения

| Что | Почему важно | Что сделать для боевого использования |
|---|---|---|
| Пароли в БД хранятся **открытым текстом** (`verify_password` просто сравнивает строки) | Утечка базы раскрывает пароли | Хешировать (например, bcrypt) |
| В `auth.py` есть запасное значение `SECRET_KEY`, если переменная не задана | Токены можно подделать, зная значение из кода | Всегда задавать собственный `SECRET_KEY` в `.env`, убрать запасное значение |
| CORS открыт для всех адресов (`allow_origins=["*"]`) | Любой сайт может обращаться к API из браузера пользователя | Указать список разрешённых адресов |
| Нет HTTPS, токен для WebSocket передаётся в адресе (`?token=`) | В журналах прокси токен может остаться виден | Включить HTTPS (wss), короткие токены |
| Сервер не проверяет, что `reaction_status` и `found_status` принимают допустимые значения | Клиент может записать произвольную строку | Проверять значения (Enum в схеме) |
| Нет ограничения числа попыток входа | Возможен подбор пароля | Ограничить попытки, добавить задержку |
| Соединения WebSocket и список обработанных событий камер хранятся в памяти одного процесса | При нескольких процессах сервера сообщения могут не дойти, а события обрабатываться повторно | Запускать один процесс или вынести обмен сообщениями в брокер (например, Redis) |
| Сервисы общаются по обычному HTTP с общим секретом в заголовке | Внутри сети Docker это приемлемо, но в открытой сети секрет можно перехватить | Закрытая сеть между сервисами или HTTPS между ними, периодическая смена `SERVICE_TOKEN` |
| Ручная фиксация сервиса камер (`POST /v1/detections`) включена по умолчанию | Любой, у кого есть `SERVICE_TOKEN`, может вызвать ложное оповещение | В боевой системе отключить: `ENABLE_MANUAL_DETECTIONS=false` |

## Рекомендации при публикации репозитория

1. Не коммитьте `backend/.env` и `backend/seed_users.json`. Перед коммитом проверьте `git status`.
2. Если пароль приложения от почты или `SECRET_KEY` когда-либо попадали в файлы, которые могли быть выложены, отзовите их и выпустите новые.
3. Для демонстрации задайте тестовым сотрудникам отдельные пароли, не совпадающие с реальными.
