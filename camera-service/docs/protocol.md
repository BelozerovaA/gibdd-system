# Протокол обмена: сервис ГИБДД и сервис камер (версия 1)

Сервис камер работает отдельно от сервиса ГИБДД: это другой процесс и другой контейнер, у него нет доступа к базе данных. Всё, что им нужно знать друг о друге, передаётся сообщениями по этому протоколу. Код с обеих сторон проверяется тестом на согласованность ([test_contract_with_backend.py](../tests/test_contract_with_backend.py)): если поле или адрес поменяют только в одном сервисе, тест упадёт.

```
        PUT /v1/watchlist  (список разыскиваемых ГРЗ)
  ┌──────────────────────────────────────────────────►┐
  │ Сервис ГИБДД                                       │ Сервис камер
  └◄──────────────────────────────────────────────────┘
        POST /api/camera-events  (камера увидела автомобиль)
```

## Общие правила

| Что | Правило |
|---|---|
| Транспорт | HTTP, тела запросов и ответов в JSON (UTF-8) |
| Подтверждение личности | Заголовок `X-Service-Token` с общим секретом `SERVICE_TOKEN`. В обоих сервисах он должен совпадать. Только латинские буквы и цифры |
| Ошибки | Тело `{"detail": "текст"}`, как у сервиса ГИБДД |
| Время | Формат ISO 8601 **с часовым поясом**, например `2026-10-12T09:00:00+00:00`. Камеры присылают UTC, сервис ГИБДД переводит в местное время (`APP_TIMEZONE`) |
| ГРЗ | Заглавными буквами без пробелов: `А123ВК43`. Обе стороны сами приводят значение к такому виду, поэтому `а123 вк43` тоже подойдёт |
| Версия | Маршруты сервиса камер начинаются с `/v1`. Несовместимые изменения будут выходить как `/v2` |

Если `SERVICE_TOKEN` не задан на стороне получателя, он отвечает `503` на все защищённые запросы. Лучше отказать, чем принимать запросы от кого угодно.

## 1. Список разыскиваемых ГРЗ: ГИБДД → камеры

Камеры сами не знают, кого искать. Сервис ГИБДД присылает им актуальный список.

```
PUT {CAMERA_SERVICE_URL}/v1/watchlist
X-Service-Token: <SERVICE_TOKEN>
Content-Type: application/json
```

```json
{ "plates": ["А123ВК43", "Е456КМ43"] }
```

Ответ `200`:

```json
{ "count": 2 }
```

| Код | Когда |
|---|---|
| `400` | Нет поля `plates`, это не список, в нём не строка, пустой ГРЗ, ГРЗ длиннее 20 символов или больше 5000 элементов |
| `401` | Неверный токен |
| `413` | Тело запроса больше 64 КБ |
| `503` | На сервисе камер не задан `SERVICE_TOKEN` |

**Каждый раз отправляется полный список, а не отдельные изменения.** Это простое правило, которое делает обмен надёжным: если запрос потерялся или сервис камер перезапустился и забыл список, следующая отправка всё исправит. Поэтому не нужно хранить «что уже отправлено».

Сервис ГИБДД отправляет список:
- при запуске;
- сразу после любого изменения розыска: добавление автомобиля, передача розыска, снятие, ответ «задержан» (отправка идёт в фоновом потоке и не тормозит ответ пользователю);
- периодически (по умолчанию раз в 30 секунд) на случай потерь;
- если сервис камер недоступен, повторяет попытку каждые 5 секунд, пока не получится.

В список попадают автомобили с активной записью розыска в статусе «В розыске». Найденные, переданные и снятые в него не входят.

## 2. Событие фиксации: камеры → ГИБДД

Когда камера «видит» автомобиль из списка, сервис камер отправляет событие.

```
POST {GIBDD_URL}/api/camera-events
X-Service-Token: <SERVICE_TOKEN>
Content-Type: application/json
```

```json
{
  "event_id": "9f3c1c7e8a5d4b6f9a2e0d1c3b4a5f67",
  "plate": "А123ВК43",
  "camera_code": "CAM-08",
  "detected_at": "2026-10-12T09:00:00+00:00"
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `event_id` | строка, 1–64 символа | Уникальный номер события. Нужен, чтобы повторная отправка не создала второе оповещение |
| `plate` | строка, 1–20 символов | ГРЗ автомобиля |
| `camera_code` | строка, 1–20 символов | Код камеры, например `CAM-08`. Сервис ГИБДД ищет камеру по этому коду |
| `detected_at` | дата и время ISO 8601 | Когда камера зафиксировала автомобиль |

### Ответы сервиса ГИБДД

Событие принято, оповещение создано (`200`):

```json
{ "status": "accepted", "alert_id": 77, "delivered": true }
```

`delivered` показывает, дошло ли оповещение до сотрудника по WebSocket прямо сейчас. Если `false`, оповещение всё равно сохранено и сотрудник увидит его при следующем открытии сайта.

Событие принято, но оповещение не нужно (`200`):

```json
{ "status": "ignored", "reason": "not_wanted" }
```

| `reason` | Почему оповещения нет |
|---|---|
| `not_wanted` | Автомобиль сейчас не в розыске (например, розыск только что сняли, а камеры ещё не получили новый список) |
| `pending_alert` | По этому розыску уже есть оповещение, на которое сотрудник не ответил |
| `cooldown` | Предыдущее оповещение было слишком недавно (`ALERT_COOLDOWN_SECONDS`) |
| `duplicate` | Событие с таким `event_id` уже обработано |

Ошибки:

| Код | Когда | Повторять отправку? |
|---|---|---|
| `401` | Неверный токен | нет |
| `422` | Неизвестная или отключённая камера, либо неверный формат полей | нет |
| `503` | На сервисе ГИБДД не задан `SERVICE_TOKEN` | нет, это ошибка настройки |
| `5xx`, сеть недоступна | Сбой на стороне сервиса ГИБДД | да |

### Повторы и идемпотентность

Если сервис ГИБДД недоступен или ответил `5xx`, сервис камер отправляет то же событие заново (по умолчанию до 3 раз, пауза растёт: 1 с, 2 с). Поле `event_id` при этом **не меняется**, поэтому, даже если первая попытка на самом деле дошла, а потерялся только ответ, второго оповещения не будет: сервис ГИБДД ответит `duplicate`.

Ответы `4xx` не повторяются: исправить их повторной отправкой нельзя.

## 3. Служебные маршруты сервиса камер

Нужны для проверки и демонстрации. Все, кроме `/health`, требуют токен.

| Маршрут | Назначение |
|---|---|
| `GET /health` | Состояние сервиса: `{"status": "ok", "cameras": 15, "watchlist": 2}`. Без токена, им пользуется Docker |
| `GET /v1/cameras` | Список камер: код, адрес, координаты, тип, ограничение скорости, работает ли |
| `GET /v1/watchlist` | Какой список ГРЗ сейчас у камер: `{"plates": [...], "count": 2}` |
| `POST /v1/detections` | **Ручная фиксация**: камера «видит» автомобиль прямо сейчас |

### Ручная фиксация

Удобно для демонстрации: не нужно ждать, пока камеры сами выберут автомобиль.

```
POST /v1/detections
X-Service-Token: <SERVICE_TOKEN>
```

```json
{ "plate": "А123ВК43", "camera_code": "CAM-08" }
```

`camera_code` необязателен, без него выбирается случайная работающая камера. ГРЗ может быть любым, не только из списка розыска: так можно проверить и случай «автомобиль не в розыске».

Ответ `200`: событие и ответ сервиса ГИБДД.

```json
{
  "event": { "event_id": "…", "plate": "А123ВК43", "camera_code": "CAM-08", "detected_at": "…" },
  "gibdd_response": { "status": "accepted", "alert_id": 77, "delivered": true }
}
```

| Код | Когда |
|---|---|
| `400` | Нет поля `plate` или `camera_code` не строка |
| `404` | Ручная фиксация отключена (`ENABLE_MANUAL_DETECTIONS=false`) |
| `422` | Неизвестная или отключённая камера |
| `502` | Сервис ГИБДД недоступен или отклонил событие (в ответе поле `gibdd_status`) |

В боевой системе ручную фиксацию отключают: `ENABLE_MANUAL_DETECTIONS=false`.

## Примеры запросов

PowerShell (русские буквы нужно передавать байтами UTF-8, иначе Windows PowerShell исказит их):

```powershell
$token = "ВАШ_SERVICE_TOKEN"
$body  = [System.Text.Encoding]::UTF8.GetBytes('{"plate":"А123ВК43","camera_code":"CAM-08"}')
Invoke-RestMethod -Method Post -Uri http://localhost:9000/v1/detections `
  -Headers @{ "X-Service-Token" = $token } -ContentType "application/json; charset=utf-8" -Body $body
```

Какой список сейчас у камер:

```powershell
Invoke-RestMethod -Uri http://localhost:9000/v1/watchlist -Headers @{ "X-Service-Token" = $token }
```

curl (Linux, macOS, Git Bash):

```bash
curl -s -X POST http://localhost:9000/v1/detections \
  -H "X-Service-Token: $SERVICE_TOKEN" -H "Content-Type: application/json" \
  -d '{"plate":"А123ВК43","camera_code":"CAM-08"}'
```

## Почему обмен идёт по HTTP, а не по WebSocket

Прежняя схема использовала WebSocket-контракт между сервисом ГИБДД и встроенным симулятором. Между сервисами выбран обычный HTTP по нескольким причинам:

- **Не нужно постоянное соединение.** Сервис камер может перезапускаться, когда угодно: следующий запрос просто пойдёт заново.
- **Повторы и идемпотентность** естественно делаются для запросов с `event_id`. С потоком сообщений пришлось бы вводить подтверждения и переподключение.
- **Простая проверка.** Любой запрос воспроизводится одной командой `curl`, ошибки видны по кодам ответов.
- **WebSocket остался там, где он нужен:** между сервисом ГИБДД и браузером или мобильным приложением. Только там сервер сам должен «толкнуть» сообщение клиенту, пока человек ничего не нажимает.
